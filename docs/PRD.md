
*Last updated: 2026-10-03 (`fix/composer-stale-size` — user report: "xdev TUI broken in the textbox input when the session have the long running, it display `TypeXaXmessage...XXXXXX`"). **The prompt box was the one row xdev never sent whole, and a pane that re-renders from its own grid showed its own fill through the gaps.**

**A frame is a delta, and that is correct.** tcell writes only a cell whose content changed (`cell.go` `Dirty`), so `paint()`'s fill of the composer row with spaces reaches the wire only where a cell actually moved. Measured over a streaming turn at 120x40 with the context dock open: **16 of the box's own 78 columns carried a glyph; 104 columns arrived in no frame at all** (`spans [[1 1] [3 3] [5 5] [10 10] [12 12] [21 76] [78 120]]`). A terminal keeps what it was sent, so the placeholder reads correctly there and always has. A pane that treats a frame as "here is the region that changed" keeps ITS value in the columns xdev never addressed, and on a pane whose clear pattern is `X` the box reads `TypeXaXmessage…XXXXXX` — xdev's own `"Type a message"` with the space columns left as the pane's fill.

**Why a long-running session and not a short one.** The box's cells move only when the transcript tail, the spinner or the clock changes. A short session is idle often enough that a whole repaint lands by luck; a long turn streams for minutes and the row rides on a frame that never comes.

**The pane's reset is silent, so there is no trigger.** A reattach, a cleared terminal, a resize that re-clears announces nothing — xdev's next frame is still a delta. That rules out a conditional repair: the only observable is the pane not receiving what it never asked for. So `App.markComposerDirty` (app.go) forces the box's rows dirty between `paint()` and `Show()`, unconditionally, and the box arrives whole every frame. Cost, measured over the same 40-frame streaming turn at 120x40: **+9.7% bytes/frame** (3191 vs 2909), bounded to the box's own rows and the main pane's columns — the context dock's 42 columns stay a delta, which is what keeps the cost proportional to the box rather than to the screen.

Deliberately not done: a `Sync()` per frame (the repair `tty_deadline.go` already uses for a dropped frame) would repair the pane too and costs a full repaint; and painting the box with a background attribute rather than spaces would change nothing on the wire, because the delta is about *content*, not ink.

Tests: `internal/tui/composer_pane_test.go` is the end-to-end proof — the REAL App over a REAL terminfo screen, each frame applied to a cell-grid pane whose grid is reset underneath a long turn, asserting the box survives; plus the wire-level assertion that the row arrives whole on 40 of 40 frames, and the cost bound. All three fail against the pre-fix shape (`markComposerDirty` removed from `draw`) and pass after, checked by stashing the fix. `composer_wire_test.go`'s delta measurement was re-pinned to the dock-open geometry, where the box stops at `rightEdge` and the panel's own columns are the delta that survives.

*Last updated: 2026-10-03 (`feat/tui-motion` — the TUI had no colour blending at all, so nothing could ease). `grep -rn 'lerp\|Lerp' internal/` returned three hits and every one was a prose comment: there was no arithmetic on a `theme.Color` anywhere in the tree. Every animation in the codebase therefore had to be expressed as a *discrete* state change — the reasoning box's focus was a boolean, and its border went from one ink to another inside a single frame. That is the whole reason #506's box "brightens": the border snapped. `theme.Lerp(a, b, t)` is the missing primitive, and it is the one thing standing between the TUI and every effect that needs a value between two theme inks. Interpolation is linear in sRGB and rounds rather than truncates, because truncating biases each mid-blend toward the dark end and a fade that goes muddy reads as a bug, not a taste choice.

The first consumer is the reasoning box's focus (`App.focusFade`, app.go). A click arms the tween at 0; each ~30fps tick advances it by `focusFadeStep` (1/6, so the ease lands in ~200ms) and keeps asking for a frame until it clamps at 1. The border then sits at `Lerp(gray_dim, accent_thinking, fade)` on its way up, and `Bold(true)` still carries the focus at the end, so a settled box paints the byte-identical style it always did. Three invariants carried the change, and each is a bug this shape invites:

(1) **Cost.** `-1` is the shipped default and means "no tween in flight", so a session that never clicks a reasoning box never enters the loop and never repaints because of it — the same discipline as the welcome sheen above it (`app.go` tick). Dropped with the boxes on replay and on `/thinking off`, or a half-drawn border outlives the block it belonged to.

(2) **Arm-on-change, not on-press.** `selection.go` starts the tween only when the focus index actually *changes*. Re-pressing the box already under the wheel leaves it alone, so a click-and-jitter cannot restart the ease and strand it part-faded forever — the tween has no timeout, by design; only a new focus or a cleared one moves it.

(3) **The render cache, which is the real trap here.** `renderKey` stamps everything a block's render reads so the per-frame cost is independent of session length — and the tween changes a border's *colour* without changing any row's text or length. A stamp that omitted it would serve one cached border for the whole 200ms and the box would snap at the end, with every test still green. So `blockKey.fade` carries `fadeBucket(focusFade)`: -1 for the sentinel, 0..8 for the fade's steps. Eight buckets is 12.5%, finer than the 1/6 the tween advances, so no visible frame is ever coalesced away.

Tests: `internal/theme/lerp_test.go` pins the blend itself — both endpoints, the rounding (255*0.5 → 128, not 127), t clamped rather than extrapolated past it, and one real theme pair rather than only the extremes. `internal/tui/focusfade_test.go` drives the real paint path and asserts the mid-fade ink differs from BOTH endpoints and equals `Lerp(gray_dim, accent_thinking, 0.5)`, that returning to the sentinel restores the resting style byte-for-byte, that a fresh App starts at -1, and that consecutive ticks never share a bucket. Confirmed red without the cache stamp — reverting `fade:` to a constant fails with the mid-fade ink reading as the resting `#BB9AF7` — so the test fails for the reason the change exists.

Follow-up, same branch: the wiring itself is now under test, which the entry above could not claim. `TestMousePressArmsTheFocusTween` and `TestMousePressOffBoxLeavesTheTweenAlone` press a *painted* reasoning box at its real screen coordinate — found by reading the simulation screen's cells for the state header, not from a layout constant — and go through `handleMouse`, the UI loop's own entry point, so the lock discipline and the arm in `selection.go` both run for real. A test that assigned `thinkFocus` itself would have stayed green with the arm deleted. Both confirmed red on the pre-fix wiring: `focus change left focusFade = 0.5, want 0 — the ease must start from the dim end, not resume`.
