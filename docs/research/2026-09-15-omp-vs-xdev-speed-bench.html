omp vs xdev — head-to-head speed benchmark

2026-09-15 36 headless runs

Same task, same model, same gateway, isolated configs, timestamp-decomposed telemetry. Reproduced from /tmp/bench2 (script bench2.sh, decomposer timeline2.py).

The claim “omp finishes tasks faster than xdev” is confirmed — and its cause is not a faster engine. Both harnesses spend 95 %+ of wall time inside the same provider round-trips, with harness switching overhead of 2–24 ms per turn on omp and ≤0.3 s total on xdev. omp wins because the same model takes fewer turns on its tool surface: xdev’s edit-grammar rejections and missing snapshot header make a mid-tier model burn 1–4 wasted provider turns per run (~7–12 s each). Where turn count cannot save it — boot and one-shot calls — xdev is decisively faster: 0.04 s vs 4.06 s fixed cost, 2–4× wall on one-shot prompts.

5 · Root causes (traced to source)

  1. Hashline rejects the colon range spelling

    The model’s RL-trained muscle memory writes PUT 15:=24:. xdev’s op regex admits only [.=]{1,2} between line numbers:

    hashlinePutRe = regexp.MustCompile(`^PUT\s+([<>])?\s*(\d*)\s*(?:[.=]{1,2}\s*(\d*))?…`)

    Every occurrence costs one full provider turn to retry. Observed error text (5× across 5 of 6 evening rounds):

    edit: edit: line 4: "PUT 15:=24:" names a range this grammar cannot express (want e.g. "PUT 3.=5:" or "CUT 5")

  2. read prints no snapshot header — so the model fabricates one

    The edit contract tells the model to quote “the header a read or a previous edit printed (never invent it)” — but xdev’s read renders bare numbered lines with no [path#TAG] header, while omp’s does. With no real tag to quote, the model invents [invoice.js#1]:

    edit: cannot read invoice.js#1: open /tmp/bench2/runs/…/invoice.js#1: no such file or directory

    An ENOENT on a path that looks like a tag teaches the model nothing; it re-reads and retries. Seen in the morning window and twice in the evening (#1, #t3).

  3. The fabricated tag silently becomes a filesystem path

    splitSnapshotTag accepts only 4–64 hex chars after #; #1 fails that test and the whole string is opened as a path:

    t := p[i+1:]
if len(t) < 4 || len(t) > 64 { return p, "" }   // "#1" → path, not tag

  4. Minimalism has a model-tier tax

    The <1000-token pi-style prompt + 400-char tool descriptions assume frontier models. On qwen3.8-flash, xdev’s runs occasionally drift: reading files via bash cat, hallucinated cd targets, and repeated verification bashes after green tests (one clean run still spent 3 turns re-running node --test). omp’s heavier prompt and always-tagged tool outputs suppress that variance — its turn count never exceeded 6 in 12 runs; xdev ranged 5–14.

6 · Measured fix (unit-proven, live-corroborated)

Three minimal diffs, built in a private worktree at HEAD fe9ebdf, kept out of the shared working tree: (1) normalize N[:=]M → N.=M before op matching; (2) read emits [path#tag] with the recorded freshness hash (notebooks unchanged), descriptions aligned and trimmed to the 400-char prompt-budget cap; (3) a non-hex #suffix whose bare name exists is refused as an unknown snapshot tag, not opened as a path. Regression tests pin the read→edit tag round-trip and the colon spelling; go test ./internal/tool ./internal/agent ./internal/tui ./internal/session green, gofmt -l clean.

Live effect: 0 grammar-error round-trips in 3/3 patched runs (5/6 unpatched had at least one). The patched wall median is meaningless this late in the provider storm (one run ate a 121.7 s upstream stall; another had a 14-turn wander with zero tool errors); the clean patched round ran 37.1 s / 6 turns against a 32.5 s / 4-turn omp control in the same window. The durable claim is the one the correlation table makes: removing the error round-trips removes the systematic 1–3 turns per run, and turn parity is where the wall-time gap lives.

7 · What xdev already proves

  • Startup budget is real: 0.02–0.15 s to first request vs omp’s 2.7–4.1 s (and 0.4–0.7 s exit vs omp’s ~0.5 s). On one-shot and short tasks xdev finishes 2–4× faster end-to-end (PONG probe median 5.1 s vs 13.2 s).
  • Decode seam is fine: xdev’s median decode on edit tasks (31.9 s) sits below omp’s (51.0 s) while carrying more output tokens (1680 vs 1316 median) — the Go SSE path adds nothing measurable.
  • Loop machinery is sound: tool dispatch is already bounded-parallel (runTools), per-entry session writes cost ~0, no queueing artifacts found in any of 22 xdev transcripts inspected.
  • Open items this exercise surfaced but did not fix: sub-1K prompts never hit the provider prefix cache; the 90 s watchdog policy turns upstream stalls into minutes with no user-visible “waiting on provider” signal; thinking-token budget drifts more on xdev’s terse prompt (422 vs 39 reasoning tokens on the same calibration prompt — sampling variance, not a config gap, worth one more measurement before acting).

8 · Method & honesty notes

  • Fixture: 3 planted bugs in invoice.js (parseFloat/off-by-one/dedup), 5 node:test cases; baseline fails 3/5; graders re-ran node --test and byte-compared invoice.test.js after each run — no arm ever touched the tests.
  • Arms run strictly serially against the one shared gateway; order alternated each round; fresh fixture + session dirs per run.
  • xdev isolated via XDEV_AGENT_DIR (bare models.yml) and herdr hooks neutralized; omp via PI_CODING_AGENT_DIR (same dir as prior rounds for continuity).
  • Binary drift caveat: three xdev binaries coexist on this machine — the installed ~/.local/bin/xdev (v0.1.0-dev) which the archived morning rounds used, the repo’s ./xdev (v0.2.0-stamped), and the clean HEAD build used tonight. Conclusions hold in both windows; morning absolute numbers describe the older binary.
  • Wall-time medians across a shared upstream that degraded 3–5× during the evening window are weak evidence; the turn-count and error-round-trip correlations (deterministic transcript facts) are strong evidence. This report distinguishes them throughout.
